RabbitMQ topology: connectivity = a file you can read

The entire topology is declared in rabbitmq/definitions.json — neither the API nor the worker ever declare queues/exchanges. They verify passively on boot (Open() in services/worker/internal/queue/queue.go; checkExchange/checkQueue in services/api/src/queue/publisher.service.ts). If the file and the code disagree, services die loudly. That's deliberate.

The three rules you must be able to explain

RuleWhereWhy
Manual acks: ack only after the final DB write.services/worker/cmd/worker/main.go — deliveryHandler; on handler error → process exits 1 → message requeuesCrash between container creation and DB write = no lost work on restart
Transient → 3 tries × 30s, then dead-queue.MaxAttempts=3, retryDecision(), RetryOrGiveUp() in services/worker/internal/queue/queue.go; the TTL is on the retry queue itself (dead-lettering is Rabbit's job, not a timer in code)Network blips and BuildKit hiccups heal themselves; exhausted failures leave evidence (attempt header + reason)
Permanent → fail now, no retry.isPermanent() (unzip.go) + permanentf()/MarkFailed in services/worker/internal/build/build.goA bad zip will never succeed the 2000th time

Message payloads — ids only

build job: { "type": "build", "deployment_id": "<uuid>" }
run/job:   { "type": "deploy", "deployment_id": "<uuid>" }   // or { type: "action", action_id: ... }
Invariant: messages carry ids only; the worker always reloads state from the DB before acting. If two workers race, DB state (not message age) decides. This is why the repair paths exist in build.Handle() — the message may be redelivered while DB says "already built".
