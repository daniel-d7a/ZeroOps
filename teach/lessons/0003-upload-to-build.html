Lesson 3: From upload to build

Objective: after this lesson, you can follow one upload from the HTTP request to a stored image_ref. You can also name the checks that occur before the code writes a byte. You can state the failures that retry, and the reason a publish failure cannot leave a ghost deployment.

1 · The API: accept, validate, commit, and publish

This work occurs before the worker starts. The order is important. If a step fails, the system does not leave a partial deployment.

StepGuaranteeExact code
Multer writes to uploads/tmp/<uuid>.part. The hard limit is 50 MB.The request body does not go to the final source path before validation. The API rejects a large upload before it computes the SHA.services/api/src/projects/projects.controller.ts — uploadStorage, FileInterceptor; MAX_UPLOAD_BYTES
The API checks ownership and active deployments.A foreign project returns 404, never 403. A second upload during an active deployment returns 409. It does not wait in a queue.assertOwned(), assertNoActiveDeployment() (up to four active statuses)
The API reads the content type. It does not trust the filename.The API rejects an HTML file with a .zip name. A rename does not fool the server.fromFile(tmp) → mime === 'application/zip'
The API computes SHA-256 during upload.The worker can prove that the file it reads is the file that the API accepted. It can detect replacement or corruption on the shared volume.sha256File()
The API renames the file to uploads/<projectId>/<sourceId>.zip.The bytes exist before a database row points to them. A crash can leave an unreferenced file, but it cannot leave a dangling row.mkdir + rename(tmp, finalPath)
One transaction writes the source row and the deployment row, and changes the project state.The source, the deployment, and the user-visible deploying badge become true together.queueDeployment() with beforeInsert; projects.status = 'deploying'
The API publishes to build.x after the commit.The broker has the job before the API says “accepted”. If the publish fails, the API compensates the deployment and the project.PublisherService.publishBuild(). On error, the code marks the deployment failed and restores the project status.
Why does the API compensate instead of publishing inside the transaction? The broker and Postgres do not share a transaction. The API commits first and compensates if the publish fails. Thus the row exists with a queued job, or the row is visibly failed. A row does not stay in queued when no message exists.

Retention runs inline after each successful upload. The API keeps the sources of the newest 5 deployments and the live and in-flight sources. It unlinks the other files and soft-deletes their rows. A prune error does not fail the deployment. The deployment already succeeded. The API writes a log entry and continues. The API unlinks the file before it updates the row. Thus a crash can retry the unlink and does not orphan the file.

Redeploy uses a stored source. By default, it uses the newest source that is not pruned. The request can set an explicit sourceId. A pruned source or a foreign source returns 404 before the API queues a job.

2 · The build worker: claim, verify, extract, and build

The worker has no state. The message contains ids only. The worker reloads each fact from the database.

The claim is the lock

ClaimBuild is one atomic UPDATE. Its WHERE clause matches only a state that the caller can move: queued, or building with a heartbeat older than 2 minutes. The winner writes worker_id and heartbeat_at. A second replica with a duplicate message gets claimed=false. It must not do the work. Thus a duplicate delivery cannot start two Railpack builds.

If the claim fails, the handler reads the current status of the row:

  • built: the deploy publish may be lost after MarkBuilt. Publish the job again. Do not rebuild (repair path).
  • building with a fresh heartbeat: the owner may be alive. Send the message to the retry exchange with the same attempt. This is a wait, not a retry. It must not use the retry budget.
  • Any other status: this is a duplicate delivery. Ack it and do nothing.

Safe unzip: check the archive before the filesystem

The zip is untrusted input. The code checks each rule against the central directory before it writes one byte. A hostile entry cannot pass before the code rejects it:

Only real I/O problems return a normal error and use the retry ladder. A full disk and EIO are examples. Archive problems never use the ladder. A retry cannot repair a zip-slip entry.

Railpack builds the image

runRailpack calls Railpack with BuildKit and --progress plain. It suppresses package-manager noise with NPM_CONFIG_LOGLEVEL=error, FUND=false, and AUDIT=false. It streams stdout and stderr to the log table in batches. The builder stops after 10 minutes. Two independent readers and a buffered channel prevent one 10 MB log line from blocking the pipe and causing a timeout.

On success, the code creates the image tag one time and stores it: proj-<projectId>:<deploymentId>. deployments.image_ref is the only place that contains an image reference. The run role reads it from the row. No other code creates or guesses the tag.

Ack rule: the worker sends the ack only after the final DB write or after the broker confirms the retry or dead publish. If the worker crashes before the ack, RabbitMQ delivers the message again. This is cheaper than recovery bookkeeping inside the worker.

Speaking exercise (60 seconds)

  1. “The API checks ownership, content type, size, and active deployments. It writes the file before the rows. Then it commits the source, deployment, and project status in one transaction. It publishes with confirms. If the publish fails, it compensates the rows.”
  2. “The worker claims with a CAS. It reloads the source path and checksum. It checks the zip before it writes any file.”
  3. “Railpack builds through BuildKit. Logs stream in batches. One CAS writes the tag to image_ref. Then the worker publishes the deploy job. The build is complete, but the app is not live yet.”
