Lesson 2: Deployment states and failure classes

Objective: after this lesson, you can read any line in build.Handle() or handleDeploy(). You can name the state of the row, the reason for the next action, and the destination of a failed message.

ZeroOps uses three state machines at the same time. If you confuse them, the code is difficult to follow:

  • Machine A: the message ladder (RabbitMQ). It controls the attempt counter and the retry and dead queues.
  • Machine B: the deployment ladder (deployments.status). The states are queued, building, built, starting, live, failed, and superseded.
  • Machine C: the user-visible states (projects.status, project_actions.status, and project_databases.status).

Machine A answers one question: will the broker send this job again? Machine B answers a second question: how far did the work go? Machine C answers a third question: what does the user see?

Machine B: the deployment ladder and all edges

stateDiagram-v2
   [*] --> queued: API projects/queueDeployment
   queued --> building: ClaimBuild (worker wins)
   queued --> failed: ClaimBuild error path / permanent at checksum+unzip+railpack+MarkBuilt
   building --> built: MarkBuilt (writes image_ref)
   building --> queued: ReleaseClaim (transient give-up or claim-crash)
   building --> failed: permanent (zip/build) OR ladder exhausted
   built --> starting: ClaimRun (run-worker wins)
   built --> failed: permanent pre-claim (no image)
   starting --> live: MarkLive (one tx)
   starting --> built: ReleaseClaim (transient give-up)
   starting --> failed: replaceContainer permanent OR ladder exhausted
   live --> superseded: MarkLive of the NEXT deployment
   failed --> [*]: user clicks Redeploy (new row, source reused)
   superseded --> [*]: image kept until pruned

All edges, their triggers, and their only writer

EdgeTriggerWriter
queued → buildingA build worker processes a build.q message.services/worker/internal/store/store.go — ClaimBuild() uses compare-and-swap (CAS) with WHERE status='queued' OR (status='building' AND heartbeat_at < now()-2min).
building → builtRailpack exits with code 0. The image proj-<id>:<deploymentId> exists.MarkBuilt() uses CAS on worker_id and writes image_ref.
building → queuedA transient failure occurs during the build. Examples are a temporary DB error or a BuildKit problem. The ladder is not exhausted.ReleaseClaim(deploymentID, workerID, "queued") releases only the claim of the caller. The row must be building or starting, and worker_id must equal the caller.
building → failedA permanent failure occurs. Examples are a checksum error, a zip security error, a Railpack exit code other than 0, or no package.json. A third transient strike also causes this edge.MarkFailed()
built → startingA run worker processes the deploy job from run.<node>.q.ClaimRun() uses the same CAS and the same 2-minute steal window.
built → failedimage_ref == "" on a built row. The user must use Redeploy. A capacity check can also cause this edge before the claim.MarkFailed()
starting → liveThe container exists, the probe passes, and the route file exists.MarkLive() uses one transaction. It sets this row to live, sets the previous live row to superseded, and sets the project to running with current_deployment_id.
starting → builtA transient failure occurs during the container or promote phase.ReleaseClaim(..., "built") returns the row to the pre-claim state, not the current state.
starting → failedThe probe fails, the image is missing, the node has no capacity, or the third strike occurs.MarkFailed()
live → supersededThe next MarkLive completes.MarkLive() uses the same transaction. The cutover is atomic, so there is no downtime window.
Use this table to predict the API behavior: the API writes only queued at insert. It reads all other states. store.go writes every other edge.

QuestionAnswerExact code
How many deliveries does a transient job get?The job gets 3 deliveries. The attempt headers are 0, 1, and 2. After that, the job goes to the dead queue.services/worker/internal/queue/queue.go — MaxAttempts=3, retryDecision()
Who waits 30 seconds?RabbitMQ waits, not application code. The retry queue has x-message-ttl:30000 and dead-letters the message back to the main exchange.rabbitmq/definitions.json
When does the ack occur?Only after the final DB write or after the dead-letter publish. If the worker crashes before the ack, the broker delivers the message again.services/worker/cmd/worker/main.go — deliveryHandler sends the ack after the handler completes. A handler error calls exit(1).

Failure classes (Machine A with Machine B)

ClassMeaningFinal row stateFinal message stateReal examples
1 · PermanentNo retry can succeed. The database row is the record.failed, with the cause in errorAcked. Nothing goes to dead.q.The zip is missing or pruned. The checksum does not match. The archive has a zip-slip path, a symlink, or no package.json. Railpack exits with a nonzero code. image_ref is empty. The image is missing at run time. The node is at capacity (MAX_RUNNING_PER_NODE). The probe fails.
2 · TransientA later try can succeed. The job climbs the ladder.failed only after strike 3. Between strikes, the row is building, built, or starting.dead.q with x-failure-reasonThe DB is unreachable. An AMQP error occurs. BuildKit is unreachable. SourceForDeployment fails. A log append fails. The project lock is busy.
3 · Infrastructure crashThe worker stopped during the job.The row stays building or starting. The heartbeat becomes stale.The broker redelivers the unacked message. There is no new attempt header.kill -9, an OOM kill of the worker container, or a Docker restart.
4 · Busy bounceAnother worker owns the job. This is a wait, not a retry.The row does not change (building or starting). The owner keeps the claim.The message is published again with the same attempt.A duplicate message arrives while the owner is alive for less than 2 minutes.

DetailReasonLocation
Actions have a partial unique index on (project_id, type) WHERE status IN ('queued','running').There is one pending action per project and type. If the user presses Restart 10 times, the system creates one row and one message.services/api/src/db/schema.ts. ActionsService.request() inserts with onConflictDoNothing.
Actions have no heartbeat and no steal.The system tolerates a redelivery while the row is running. ClaimAction claims only queued rows. A second claim of a running row is skipped because the work is idempotent.ClaimAction and actionSkip() in run.go. The test is in services/worker/internal/run/run_test.go.
FinishAction also accepts 'queued'.If the system gives up before a claim, the row must still reach a terminal state. The system does not leave a zombie row in queued.store.go FinishAction()
For stop, route.Delete occurs before the container stops.The URL stops before the compute stops. The user does not see a 502 window.runAction() stop case in run.go
MarkFailed changes the project in a cascade.The same transaction sets projects.status='failed' if the project was deploying.store.go L361-380
Each project has one database.Later deployments find ready and skip all DDL.provision.Ensure(), MarkDatabaseReady()
