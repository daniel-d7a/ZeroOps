Lesson 4: From run to route

Objective: after this lesson, you can follow the deployment cutover in order. You can explain what happens when a new container fails its probe. You can also explain why a student container has no Traefik labels and cannot reach another project.

Before a container: lock, capacity, and claim

StepReasonCode
Advisory project lockA stop action must not occur at the same time as a deploy for the same project. A busy lock is transient. The retry TTL is the backoff.services/worker/internal/store/store.go — TryProjectLock()

The four operations in replaceContainer

1 · Network isolation is structural

  • EnsureProjectNetwork creates net-<projectId> with the label platform.project. The operation is idempotent.
  • Traefik joins that network and resolves the container by name. If the project has a database, student-db joins the network too. The app reaches the database at the fixed hostname student-db.
  • The student container joins only that network. It never joins platform, edge, or db. Two projects are isolated because they never share a network.

2 · The container has limits by default

ControlValueReason
CPU, memory, and swap0.5 CPU, 1 GiB, swap = memoryA student app cannot starve the host. No swap means the memory limit is a real limit.
PIDs256Fork-bomb guard.
Restart policyon-failure:5A crash recovers a few times. A manual stop does not restart.
Log driverjson-file, 10 MB × 3The disk use per container is bounded.
no-new-privilegessetPrivilege escalation guard. Phase 3 still needs a non-root user, all capabilities dropped, and a read-only rootfs.
Labelsplatform.project, platform.deploymentThese labels support lifecycle and cleanup only. There are no Traefik labels.

The worker loads the environment each time it creates a container. It decrypts the user variables, then adds PORT=3000, then adds DATABASE_URL when the project has a database. Thus a restart applies changed environment variables, and a running container keeps its old values. The values go directly into the container spec. The system never logs them.

3 · The health probe is a real gate

The worker is not on the student network. It cannot dial the app by name from its own interfaces. JoinForProbe attaches the worker temporarily. The worker dials <container>:3000 until the app accepts TCP or 60 seconds pass. Then the worker disconnects with a new context because the job context may be cancelled.

A failed probe removes only the new container. The old container and its route file do not change. Thus a broken deployment never takes the live site down. This is the difference between a failed deployment and an outage.

4 · Routing uses a file, and the cutover uses a rename

Traefik uses two providers:

  • Docker provider for platform services. exposedByDefault=false. Only api and web have labels.
  • File provider for student apps. The worker writes /dynamic/proj-<projectId>.yml. The file has one router and one service per project and points to http://app-<deploymentId>:3000.

The writer writes proj-<id>.yml.tmp and renames it to the final name. Rename is atomic on the shared volume. Traefik never reads a partial file. The worker writes the route only after the probe passes. Traffic switches in one step, and the old route stays until then.

Finish: one transaction, then cleanup

MarkLive is one transaction:

  1. CAS this deployment: starting, worker = me → live.
  2. Set the previous live deployment to superseded in the same project.
  3. Set the project to running with current_deployment_id = this.

Thus the console cannot show two live deployments. It cannot show a running project with a deployment that is not live. After the transaction, the worker prunes old images. It keeps the live image and the previous image because a restart of the superseded deployment needs its image. A prune failure writes a log entry. It does not fail the deployment.

Actions: stop, start, and restart

ActionOrderReason
stoproute.Delete → stop containers (10 s grace) → project stopped + desired_state=stoppedThe URL stops before the compute. There is no 502 window. Docker’s restart policy does not undo a manual stop.
startReuse the stopped container if it exists → create or verify the network and Traefik, probe, write route. If the container does not exist, rebuild with replaceContainer.The fast path does not rebuild. A pruned container still has its image.
restartAlways use replaceContainer from image_ref, then set the project to running.The worker recreates the container with new environment variables. A short downtime is accepted (plan §8.3.4).

All three actions use the same per-project lock, action claim, and transient ladder. If a dead worker leaves an action row in running, a redelivery runs the action again. The open-action index does not stay blocked. See Lesson 7.

Recovery cases to remember

SituationCode behavior
A new deployment fails its probe.The worker removes the new container. The old container and route do not change. The deployment becomes failed.
The worker crashes after the route write and before MarkLive.A redelivery steals the claim after the heartbeat window and runs the cutover again. The route write is idempotent.
Old-container cleanup fails.The system writes a log entry only. The app is already live. A retry would probe and reroute again, which is worse.
The image is missing at run time.Permanent ErrImageMissing → “use Redeploy”. A retry cannot create the image.
Traefik is down during a deployment.The container is on net-project, but Traefik does not read the route file. The probe still passes and the worker writes the route. The URL starts to work when Traefik returns. Platform routing is a single point of failure.
