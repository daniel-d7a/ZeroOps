Lesson 11: Startup reconcile

Objective: after this lesson, you can explain what the worker does at startup. You can trace how a running project comes back after a machine reboot. You can also explain why a stopped project stays stopped.

Why this duty exists

Student containers are not compose services. Docker keeps them on the node, but a machine reboot can leave them stopped. The platform DB still says desired_state='running'. Without a reconcile, the row and the real container disagree forever. The user must press Start.

The reconcile closes that gap. It compares the desired state in the DB with the real Docker state. It queues a start action only when the project should run and the container does not.

The reconcile runs before the run queue is consumed. The start messages that it publishes wait in the queue until the consume loop starts.

The decision

The rule is small. A project needs a start action only when all three conditions are true:

  1. The project has a current deployment.
  2. No queued or running action exists for the project.
  3. The container for that deployment is not running.
Desired stateCurrent deploymentOpen actionContainerResult
runningyesnorunningNo action. The project is healthy.
runningyesnostopped or goneQueue a start action.
runningyesyesstoppedSkip. The open action owns the project.
runningnonononeSkip. There is nothing to start.
stoppedyesnostoppedSkip. The user wants it stopped.

The pure rule is shouldStart. The unit test is in services/worker/internal/run/reconcile_test.go.

The steps in code

  1. List the candidates. ReconcileCandidates selects projects with node_id = this node and desired_state = 'running'. It also reports whether an open action exists. See services/worker/internal/store/store.go.
  2. Inspect the container. The name is app-<deploymentId>. ContainerRunning returns false for a missing container, so “gone” and “stopped” take the same path. See services/worker/internal/docker/docker.go.
  3. Insert one start action. QueueStartAction uses WHERE NOT EXISTS to block a second open action. The partial unique index project_actions_open_idx is the second guard. A conflict returns created=false.
  4. Publish the job. PublishAction sends {"type":"action","action_id":...} to run.x with the node id as the routing key. The publish uses confirms and the mandatory flag.
  5. Compensate on publish failure. If the publish fails, the worker marks the action failed with the publish error. It does not leave a queued row with no message.
  6. Run the normal start action. The run handler starts the stopped container when it exists. When the container is gone, it rebuilds from image_ref. It probes the app, writes the route, and sets the project to running.
Invariant: the reconcile never creates a deployment and never rebuilds an image by itself. It only creates a start action. All container work stays in the run handler.

Why multiple replicas are safe

  • Every run replica on the node can run the reconcile. The DB decides which one wins.
  • QueueStartAction inserts at most one open start action for a project.
  • If two workers both see a stopped container, one insert wins and the other returns created=false.
  • If a user action is already open, the reconcile skips the project.
  • The start action itself takes the per-project advisory lock, like every other run job.

What it does not do

Not handledReason
Auto-redeploy a crashed appPlan §8.7 crash policy: Docker restarts the same image up to 5 times. The platform does not redeploy automatically.
Rewrite a route when the container is already runningThe route file survives on the shared volume. The container check is the signal.
Touch a project with desired_state='stopped'A manual stop must survive a worker restart.
Reconcile another node’s projectsEach node has its own run.<node>.q and its own containers.
Repair an unroutable publishThat is a separate gap. The reconcile only handles container state.

Failure behavior

FailureResult
Docker inspect fails for one projectThe worker logs the error and continues with the next project.
The DB query for candidates failsThe worker logs startup reconcile failed and still starts its consume loops.
The action insert failsThe worker logs the error and continues. The next restart tries again.
The publish failsThe action is marked failed with publish failed: ....
The start action failsThe normal action failure path records the error on the action row.

The reconcile is best effort. One bad project must not stop the worker from serving the others.
