  1. Short summary: “ZeroOps has a control plane that accepts a zip. A worker fleet builds and runs the zip. An edge proxy gives each app a hostname.”
  2. Split by trust: the API handles requests and owns the DB schema and uploads. The worker acts asynchronously and owns the Docker socket and routes. Neither writer changes the transitions of the other.
  3. Follow one deployment: signup → project → upload. The upload writes the file first, then the row, then publishes with compensation. The build claims the row, verifies the checksum, unzips safely, runs Railpack, and stores image_ref. The run stage provisions, creates net-<id>, creates the container, probes it, writes the route file atomically, and sets live. Stop, start, and restart use the same pipeline.
  4. Two important guarantees: a failed deployment leaves the old version live. The queue tolerates crashes because the ack is manual and claims use CAS steals.
  5. The edge: Traefik uses the Docker provider for the console and the file provider for student apps. The console is same-origin, so there is no CORS. Only port 8080 is published.
  6. Recovery: at startup the run role compares desired_state='running' with the real container. It queues one start action when the container is stopped or gone. A project with desired_state='stopped' stays down.

Invariants and their reasons

InvariantReasonEffect of a violation
State ownership: the worker writes the transition statuses. The API writes only during a request.One writer for each field removes distributed write races without locks.Two writers produce contradictory statuses and lost updates.
deployments.image_ref is the only image reference.One durable source prevents different tag reconstruction across retries.Run pulls a nonexistent tag. Builds and runs disagree.
The worker checks MIN_SCHEMA_MIGRATION. Migrations belong to the API.Old worker code against a new schema is a silent data bug. Fast failure is safer.The worker corrupts writes or crashes during a job.
Use 404, not 403, for the resource of another user.A 403 confirms existence and leaks ids across tenants.Users can enumerate the projects of other users.
No Traefik labels on student containers. Use the file provider only.The worker controls the exact time that a route appears, after the probe.Traefik routes to an unhealthy container. A failed deployment causes downtime.
Environment values use AES-256-GCM. They are never logged or returned to another user.Environment variables contain database URLs and secrets. The DB is not a trust boundary for them.A credential leak through a DB dump, logs, or an API response.
Only the worker and Traefik (read-only) mount the Docker socket.The socket is equivalent to root on the host.A compromised app or the API escapes the sandbox.
Student containers join only net-<projectId>.The isolation is structural, not a policy.Cross-project DB or app access (scenario 08 would fail).
Messages contain ids only. The worker reloads state from the DB.A message cannot contain stale or false state.The worker acts on an old snapshot.
Ack only after the final DB write.A crash before the write must cause a redelivery.Jobs are lost but look successful.
Same-origin only. The console splits by host and path.There is no CORS surface. Cookies stay same-site. CSRF defenses work.CORS misconfiguration and weak cookies.

“Where is X?” rapid exercise

QuestionAnswer
Where does the API accept and store a zip?services/api/src/projects/deployments.service.ts and projects.controller.ts — multer → content sniff → sha256 → file → transaction row → publish, with compensation.
Where does a build start?services/worker/internal/build/build.go — Handle: claim, checksum, unzip, Railpack, store image, publish run.
Where is a container created?services/worker/internal/run/run.go — handleDeploy (limits, network, environment, probe).
Where is the route file written?services/worker/internal/route/route.go — temp file and rename after the probe.
Where are sessions and CSRF handled?services/api/src/auth/ (argon2id, session regenerate) and services/api/src/auth/csrf.guard.ts.
Where are environment variables encrypted?services/api/src/common/crypto.ts and services/api/src/projects/env.service.ts. The worker decrypts only at container create.
Where is the database provisioned?services/worker/internal/provision/provision.go — role, database, extensions, revoke.
Where are retries configured?rabbitmq/definitions.json (30-second TTL, dead queues) and services/worker/internal/queue/ (ack and nack logic).
Where is the console polling?services/web/src/components/project/ — project 2.5 s, deployments 2 s while active. The log cursor loop is in DeploymentsTab.vue.
Where does the system prevent an old worker from using a new schema?services/worker/internal/store/store.go — CheckSchema against MIN_SCHEMA_MIGRATION.

Failure-class exercise

SymptomFirst place to look
A deployment is stuck in queued.Was the message published? Check the queue depth, routing key, and worker roles. Then check the claim query.
A deployment is stuck in building.Read the worker logs, BuildKit health, and unzip or Railpack output. Check for a stale heartbeat that should be stolen.
The deployment is failed with no error text.Check the permanent and transient classification, the failure write path, and the error field.
The app is live but the URL returns 404.Does the route file exist in /dynamic? Is the student container on net-*? Is Traefik on that network? Is the Host header correct?
The old version still serves after a new deployment.This is expected if the new probe failed. Check the new deployment status and the container logs.
A write returns 401.Check the CSRF header and the session before you suspect ownership.
Login or signup returns 429.The auth throttle is 10/min. The tests back off.
