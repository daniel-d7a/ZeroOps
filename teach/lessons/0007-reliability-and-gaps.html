Lesson 7: Reliability and current gaps

Objective: after this lesson, you can name the behavior for each crash point. The crash points are a killed worker, a broker outage, a DB outage, an unroutable publish, and a node reboot. You can also identify which behaviors are known gaps, not designed recovery.

State of this lesson: 2026-10-26. Phase 1 of docs/FIXLIST.md is shipped. Phases 2 and 3 are not.

The ack contract is the safety net

unacked, invisible to other consumers"] --> H["handler"]
  H -->|"success"| DB["final DB write"]
  DB --> A["ack"]
  H -->|"transient"| R["release claim
publish retry (attempt+1)"]
  R --> A
  H -->|"3rd delivery"| DEAD["publish dead
mark failed in DB"]
  DEAD --> A
  H -->|"permanent"| FAIL["MarkFailed"]
  FAIL --> A
  H -->|"infrastructure error"| CRASH["return error → main exits"]
  CRASH --> RQ["connection closes
unacked message requeues"]

There is no separate recovery daemon for jobs. The broker keeps the unacked message. The DB row is the record. The worker acks only after the last write. If the worker crashes before the ack, the message returns, possibly to another replica.

Use this rule: “Message first, DB next, ack last.” On give-up, the broker confirms the retry or dead publish before the worker writes the failure and acks. Thus a failure never exists only in memory.

1 · Claims, steals, and busy bounces

Claims are the only mutual exclusion for jobs:

  • ClaimBuild and ClaimRun are single UPDATEs. Their WHERE clause matches only the allowed source state.
  • The claim writes worker_id and heartbeat_at. After 2 minutes without a heartbeat, another replica can steal the job.
  • A duplicate delivery while the owner is alive gets claimed=false. For building or starting with a fresh heartbeat, the worker publishes to the retry exchange with the same attempt. This is a wait, not a retry. It must not use the failure budget.
  • Actions are different. They have no heartbeat column. A redelivered message for a row that is still running is executed again. The previous holder died with the message unacked, so this is the only way the broker can redeliver it. This prevents a permanent stop failure. The per-project lock keeps the effect small.

2 · The retry ladder

DeliveryAttempt headerOn transient failure
1st0Publish to the retry exchange with attempt 1.
2nd1Publish with attempt 2.
3rd2The next attempt would be 3. Publish to the dead queue, mark the row failed, and ack.

Thus a transient job gets three deliveries, which is two retries. The retry queue has a 30-second TTL and dead-letters to the main exchange. RabbitMQ waits, not the worker. This matches plan §6. It conflicts with the “3×” wording in AGENTS.md. This is an open alignment item.

3 · Crash-point matrix (current behavior)

Crash or failure pointCurrent behaviorRecovery mechanism
The worker is killed during a build.The row stays building. The message is unacked and redelivered.The redelivery waits for the 2-minute stale heartbeat, then steals the row and rebuilds. If the image exists, the worker skips Railpack.
The worker stops after Railpack and before MarkBuilt.The row is still building. The image exists on disk.The claim steal and the imageExists repair path skip the build and write image_ref.
The worker stops after MarkBuilt and before the deploy publish.The row is built with no run message.The redelivery sees built and publishes the deploy job again.
The worker stops during a deployment after the route write.The new container may be live and routed. The row is still starting.The claim steal runs replaceContainer again. The route write and the attachment are idempotent. MarkLive then wins.
The worker stops while an action is running.The action row stays blocked. The API open-action index blocks a new action of the same type.The redelivery executes the running action again. FinishAction can move it to a terminal state.
The DB is down during a try/catch block.The handler returns an error and the worker exits. The message requeues.The worker restarts until the DB returns. No job is lost. The system does not report a false success.
The broker is down at publish time.The API upload publish throws. The deployment becomes failed, the project is restored, and the API returns 502.The system does not leave a ghost queued row.

The platform stack goes down.Student containers are not compose services. They can survive as unreachable zombies.scripts/down.sh stops containers with the platform.project label. A plain docker compose down leaves them.
Old-container cleanup fails after a good probe.The new version is live and routed. The old container remains until the next cleanup.The system writes a log entry only. This is deliberate. A retry would probe and reroute again.

Backlog items

  • BASE_DOMAIN drift: the Traefik console rules hardcode console.localhost. The worker builds student routes from BASE_DOMAIN. If one value changes and the other does not, half of the system breaks.
  • Retry wording drift: three deliveries and two retries, compared with “3×” in AGENTS.md.
  • deployments.container_name and attempt are unused columns. No code writes them. Remove them or populate them deliberately.
  • Upload orphan: if the code fails after the file rename, it unlinks the wrong path and leaves an orphan zip.
  • Route temp files are in Traefik’s watched directory (.tmp). This can cause parse flapping. Write them outside the watched directory or use an ignored prefix.
  • E2E cleanup force-removes all app-* containers and net-* networks. Add a label filter before it runs on a shared host.

Speaking exercise (60 seconds)

  1. “Jobs are safe because the broker holds unacked messages. The worker acks only after the final DB write.”
  2. “Claims are CAS updates. A stale heartbeat permits a steal. A duplicate bounces with the same attempt while the owner is alive.”
  3. “Phase 1 fixed the incorrect behavior: polling, wedged actions, zombie student containers, and log growth.”
  4. “Known gaps are: no runtime logs or SSE, and an unroutable publish that only logs. The sandbox also uses root with default capabilities.”
