Lesson 5: One authenticated request

Objective: after this lesson, you can follow a console request through Traefik, session middleware, CSRF, role checks, validation, and ownership. You can also explain each rejection as 401, 403, or a deliberate 404.

1 · The same-origin boundary starts at Traefik

ZeroOps has no CORS middleware because it has no cross-origin API. Traefik has two Docker-provider routers on the console.localhost host:

RuleTargetResult
Host(console.localhost) && PathPrefix('/api')api:3000API calls have the same origin as the console. The browser sends the session cookie automatically.
Host(console.localhost)web:80 (dev: 5173)All other paths use the static SPA. Caddy serves index.html for an unknown path.

A cross-origin attacker can send the cookie, but cannot read the CSRF token. The attacker also cannot set a custom header because the server never allows the preflight request. Thus the double-submit CSRF design works without CORS.

2 · Sessions: cookie, store, and two time limits

Session data is in Postgres, not in the cookie. The cookie contains only the session id.

SettingValueReason
CookiehttpOnly, SameSite=Lax, secure: autoJavaScript cannot read the cookie. A cross-site POST does not send it. Secure becomes active when the request uses HTTPS.
Rolling idle timeout7 days, refreshed on each requestAn active user stays signed in.
Absolute cap30 days from startedAtSessionGuard destroys the session after 30 days, even when the session is active.
Storesessions table through connect-pg-simpleThe session survives an API restart and is shared by API replicas.
Trust proxy1There is one Traefik hop. Rate limiting sees the real client IP, not the IP of Traefik.

Login and registration details

  • argon2id hashing (@node-rs/argon2).
  • Timing parity: the code checks a missing email against a dummy hash. Registration hashes the password before the duplicate check. Both paths have the same cost, so response time does not reveal registered users.
  • Session fixation: login calls req.session.regenerate() before it writes the uid. Then it creates a new 32-byte CSRF token. Code must use req.session after regeneration. A captured pre-login id is useless.
  • Disabled accounts: login returns 403. /auth/me destroys the session if the user became disabled after login.
  • Self-healing token: /auth/me creates a CSRF token for an old session that does not have the field.

3 · CSRF: the global guard for state changes

flowchart TD
  R["request"] --> M{"GET / HEAD / OPTIONS?"}
  M -->|"yes"| PASS["pass"]
  M -->|"no"| U{"session has uid?"}
  U -->|"no"| PASS
  U -->|"yes"| H{"X-CSRF-Token equals
session.csrf in constant time?"}
  H -->|"yes"| PASS
  H -->|"no"| F["403 invalid CSRF token"]

CsrfGuard runs for all requests. An anonymous state-changing request passes the guard. It then stops at SessionGuard on the controller with 401. The comparison uses timingSafeEqual, so a token match does not leak prefix timing.

The console keeps the token in memory. login and /auth/me return csrfToken. The fetch wrapper sends x-csrf-token. The XHR upload path does the same because fetch cannot report upload progress.

4 · Guards and the 401 / 403 / 404 ladder

CheckFailureLocation
No live session401SessionGuard on each protected controller
Session is past the absolute cap401. The session is destroyed.SessionGuard
A session-backed write has no valid CSRF token403CsrfGuard
The user is not an admin403RolesGuard. It reads the role from the DB, so a role change applies immediately.
The project belongs to another user or does not exist404, deliberately not 403ProjectsService.get, DeploymentsService.assertOwned, env service
The user reached a quota, used a duplicate slug, or has an open action403 or 409services
Malformed body or bad UUID400global ValidationPipe, ParseUUIDPipe
Use 404, not 403, for the resources of other users. A 403 confirms that the id exists and belongs to somebody. A 404 keeps the existence of the resource private. Admin routes read any resource and use the role guard instead.

All protected routes are in api-map. The pattern is consistent:

POST   /api/auth/register        public, throttled 10/min
POST   /api/auth/login           public, throttled 10/min
GET    /api/auth/me              SessionGuard
GET    /api/projects             SessionGuard
POST   /api/projects             SessionGuard + CSRF
POST   /api/projects/:id/deployments   SessionGuard + CSRF + multipart
GET    /api/projects/:id         SessionGuard + ownership
GET    /api/admin/users          SessionGuard + RolesGuard(admin)

5 · The console applies the same rules, but not as security

The Vue router guards improve the user experience. They are not security:

  • A beforeEach reads ['me'] through TanStack Query. An unauthenticated navigation redirects to /login?redirect=….
  • requiresAdmin prevents the render of an admin page for a non-admin. The API RolesGuard is the real enforcement.
  • The session cookie is httpOnly. The client never stores the session token. It stores only the CSRF token in memory.
  • Every fetch sets credentials: 'include' explicitly, although requests are same-origin. This documents the intent.

Speaking exercise (60 seconds)

  1. “Traefik sends /api on the console host to the API. It sends all other paths to the SPA. Thus there is no CORS.”
  2. “The session is a Postgres-backed httpOnly cookie. It has a 7-day rolling idle timeout and a 30-day absolute cap.”
  3. “Global throttling and CSRF run first. Protected controllers add SessionGuard. Admin routes add RolesGuard, which reads the role from the DB.”
  4. “Services enforce ownership with 404, not 403. They check quotas and reserved names before they touch the DB.”
