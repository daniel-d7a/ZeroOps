Lesson 6: Secrets and databases

Objective: after this lesson, you can explain how an environment variable goes from the console to a container without a log entry. You can also explain how a project gets one Postgres role and database that no other project can use.

Two encrypted values, one format

ZeroOps encrypts two kinds of secret with the same algorithm and the same byte layout:

  • User environment variables (env_vars.value_encrypted).
  • Per-project database passwords (project_databases.password_encrypted).

PropertyValueReason
CipherAES-256-GCMIt gives confidentiality and authentication. A changed ciphertext fails to decrypt. It does not return garbage.
KeyENCRYPTION_KEY, 64 hex charactersThe API validates the key at request time and the worker validates it at startup. A bad key stops the process. The process does not use a default.
NonceA fresh 12-byte random IV for each encryptionThe same plaintext encrypts differently each time.
Layoutbase64(iv || tag || ciphertext)Go and TypeScript must read the rows of each other. GCM uses tag-after-ciphertext order. The code rearranges it explicitly.
Decryption locationThe API list endpoint (owner) and the worker containerEnvThe system never writes values to logs or messages. It never returns them to a non-owner.
Users cannot override reserved keys. The API rejects PORT and DATABASE_URL from users. The worker adds its own values last. The platform owns the port (3000) and the database URL. A student environment variable cannot redirect the health probe or the DB connection.

1 · Write an environment variable

The endpoint is PUT /api/projects/:id/env/:key. A bulk PUT /api/projects/:id/env supports the .env editor. The API enforces these rules before encryption:

RuleLimit
Key format^[A-Z_][A-Z0-9_]*$, at most 128 characters
Value1 byte to 4 KB UTF-8
Reserved keysPORT, DATABASE_URL
Quota50 variables per project. An update of an existing key does not use the quota.
Ownership404 if the project belongs to another user

Bulk apply is all-or-nothing. The API validates each key first. It computes the quota against the final state. Then one transaction does one multi-row upsert and the deletes. A pasted .env with an invalid key writes nothing and names the key.

On the console, Save sets a local changed flag and shows “restart required”. This message is correct. The running container received its environment at create time. Only start, restart, or a new deployment reads the values again.

2 · Read an environment variable at container create

sequenceDiagram
  participant W as run worker
  participant DB as platform-db
  participant D as Docker
  W->>DB: Store.EnvVars(projectId)
  DB-->>W: key + ciphertext rows
  W->>W: crypt.Decrypt each value
  W->>W: append PORT=3000
  W->>DB: LoadDatabase if wantsDb
  W->>W: decrypt db password, build DATABASE_URL
  W->>D: RunStudent(env list)
  Note over D: values exist only in container config

The worker builds the environment slice in memory and passes it to Docker. No log line prints it. No message on the broker contains it. The API does not return it to a non-owner. The owner can list the values and receives plaintext. The invariant protects non-owners, logs, and messages. It does not hide a user’s own values from that user.

3 · Provision a project database

When wantsDb is true, the run role provisions the database before it starts the container. Each deployment calls the same routine, so the routine must be idempotent.

flowchart TD
  E["provision.Ensure(projectId)"] --> I["identifier = p_ + uuid without dashes
must match ^p_[0-9a-f]{32}$"]
  I --> PW["24 random bytes → base64url password"]
  PW --> ENC["encrypt password"]
  ENC --> ROW["EnsureDatabaseRow
insert if missing, else return stored row"]
  ROW --> RD{"status already ready?"}
  RD -->|"yes"| DONE["skip all DDL"]
  RD -->|"no"| DEC["decrypt stored password"]
  DEC --> DDL["applyDDL"]
  DDL --> ROLE["role exists? ALTER PASSWORD : CREATE ROLE ... CONNECTION LIMIT 10"]
  ROLE --> DB["database exists? CREATE DATABASE ... OWNER role"]
  DB --> REV["REVOKE CONNECT ON DATABASE ... FROM PUBLIC"]
  REV --> READY["MarkDatabaseReady"]
DecisionReason it is safe
Row before DDLA crash between the row and the DDL leaves a record that can resume. It does not leave an unknown database.
Identifier from the project UUIDThe code validates db_name and db_user against one regexp before interpolation. SQL cannot parameterize identifiers, so the allowlist is the defense.
Stored password is authoritativeEach retry uses the same password. A recreated row does not lock the app out of an existing database.
Idempotent DDLThe code uses ALTER if the role exists and CREATE only if it is missing. It revokes on each run. The retry ladder can repeat the DDL.
Revoke CONNECT from PUBLICWithout the revoke, each login role on student-db could connect to each project database. This is the cross-project isolation gate.
Student-db joins net-<projectId>The app reaches the database at the fixed hostname student-db. The database is not on a shared database network with other students.

The injected URL

DATABASE_URL=postgres://p_<32hex>:<base64url>@student-db:5432/p_<32hex>

The password uses base64url, so it needs no percent-encoding in a URL. The worker builds the URL from decrypted parts. The API never exposes it. The Database tab shows only the status, database name, and user.

4 · Schema ownership and migrations

The API owns the platform schema and the migrations (Drizzle). The worker never runs a migration. It starts only if the platform schema is at least as new as it expects:

flowchart LR
  M["compose: migrate one-shot
node dist/db/migrate.js"] --> DB["drizzle.__drizzle_migrations"]
  DB --> A["api starts"]
  DB --> W["worker CheckSchema
row count ≥ MIN_SCHEMA_MIGRATION"]
  W -->|"too old"| X["refuse to start"]
  W -->|"ok"| J["consume jobs"]

All worker SQL is in services/worker/internal/store. The API writes only request-time state. That split keeps the deployment state machine auditable in one file.

What is not hardened yet

  • Student containers run as root with the default Docker capabilities. Only no-new-privileges is set. Phase 3 needs a non-root user, CapDrop: ALL, a read-only rootfs, and default seccomp.
  • There is no key rotation flow. ENCRYPTION_KEY is one key for all rows. A rotation requires the re-encryption of each secret.
  • The quota checks for projects and environment variables use check-then-act. Concurrent requests can go over a limit. A DB arbiter is on the backlog.

Speaking exercise (60 seconds)

  1. “Environment values and DB passwords use AES-256-GCM with a fresh IV. The format is base64(iv||tag||ciphertext). The API writes them. The worker decrypts them only when it creates a container.”
  2. “The platform owns PORT and DATABASE_URL and rejects them from users. Thus the worker can add them safely.”
  3. “Database provisioning writes the row first. It derives SQL identifiers from the UUID and validates them against a regexp. It creates a role and database, revokes PUBLIC connect, and marks the row ready.”
  4. “Environment changes take effect only in a new container. Thus the console shows restart required.”
